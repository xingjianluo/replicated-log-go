# replicated-log-go：本地可运行的复制日志一致性组件

一套用 Go 实现的简化 [Raft](https://raft.github.io/) 复制日志一致性算法，
配套一个**可注入的确定性执行环境**（逻辑时钟 + 可分区/乱序/重复的网络 +
可保留的"磁盘"），用于在本地稳定复现网络分区、节点重启、消息重复/乱序等
异常，并验证各节点的日志状态始终一致、且判定过程可解释。

## 目录结构

```
raft/                 与执行环境无关的 Raft 算法
  types.go            消息/条目/配置/拒绝原因等核心类型
  errors.go           可区分的提案错误（非领导者、变更在途、已压缩……）
  node.go             节点状态机：Tick/Step、提案、提交推进、状态应用
  election.go         领导者选举：任期、投票限制、当选 noop
  replication.go      日志复制：一致性检查、冲突显式截断、快速回退
  snapshot.go         快照安装：落后节点先装快照再追增量
  storage.go          Storage 接口 + 内存实现（冲突截断/压缩语义）
  membership.go       多数派计算、单成员变更、配置序列化
  apply.go            幂等 KV 状态机（按日志位置去重，可重放）
sim/                  确定性执行环境
  env.go              事件驱动模拟器：逻辑时钟、重启、断言辅助
  network.go          分区矩阵、随机延迟（乱序）、丢包、重复投递
  disk.go             跨"重启"保留的内存磁盘
  logger.go           带逻辑时间戳的诊断日志
cmd/demo/             六个阶段的端到端演示
*_test.go             确定性场景测试（raft 包内 + sim 包内）
```

## 一致性协议要点

### 1. 领导者选举与多数派约束

- 时间被离散化为 tick；选举超时在 `[electionTick, 2*electionTick)` 内
  由**注入的随机种子**决定，同一种子结果完全一致。
- 候选者先递增任期、**先持久化自投、再并行为每个投票成员发 `RequestVote`**，
  因此同一任期内一张选票至多投给一个候选者，同一任期至多产生一个领导者。
- 投票限制（Raft 5.2.1/5.4.1）：本任期未投过他人，且候选者日志
  `(最后任期, 最后位置)` 至少与本地一样新，才允许投票。
- 赢得 `floor(n/2)+1` 票才当选；**少数派分区永远凑不齐多数派**，
  其陈旧领导者的提案既不会被提交，也不会泄漏到多数派。
- 当选立即追加一条本任期 noop 条目并广播：既宣告领导权，又让前任
  遗留的已复制条目可以在新任期被安全提交。
- 已不在最新投票配置中的节点**不主动发起选举**，其拉票请求也会被
  明确拒绝（`unknown-node`），避免被移除节点干扰在任集群。

### 2. 日志复制与提交语义

- 领导者按 `(prevLogIndex, prevLogTerm)` 做一致性检查；
  不匹配时**显式截断冲突点及其之后的全部本地日志**再追加，
  拒绝原因 `log-gap`，并携带 `RejectHint` 帮助领导者一次性回退整个冲突任期。
  冲突是被修正、被记录的，不是静默覆盖。
- 同位置同任期且内容一致的条目重复到达时幂等保留；
  若同位置同任期但内容不同（例如新节点引导配置与集群分叉），同样按
  冲突截断处理。
- 提交规则（防 Figure 8 错误）：**只有多数派复制了"当前任期"的条目，
  才允许推进 commit**；旧任期条目不能仅凭副本数被提交，必须等当前任期
  的 noop/新条目复制到多数派后一起提交。
- 领导者切换不会回滚已提交条目：高任期领导者同步时，跟随者只截断
  **未提交**的冲突尾部，commit 位置单调不减。
- 状态机按日志位置幂等应用（`appliedIndex` 去重）；节点重启重放
  已提交区间时同一位置重复 Apply 不产生二次效果。

### 3. 日志压缩（快照）

- `TakeSnapshot` 以"已应用位置"为界：状态机产出快照字节，存储丢弃
  快照点（含）之前的日志，之后的增量日志原样保留。
- 落后到压缩点之前的节点走 `InstallSnapshot`：整体恢复状态机与配置，
  再从 `snapshot.Index+1` 增量追赶。
- 比本地更旧的快照被拒绝（`snapshot-stale`）；快照恢复只让 commit
  前进到快照点，**绝不回退**，也不影响任何已提交状态。

### 4. 成员变更

采用 Raft 论文中"**一次只变更一个成员**"的规则：

- 同一时刻至多一个在途变更（否则返回 `change-pending`）；
- 添加已存在节点、移除不存在节点返回明确的 `noop-change`；
- 新节点先用"现有成员 + 自己"的初始配置在空白磁盘上创建
  （`Env.PrepareNewNode`），在加入配置提交前它无法赢得选举；
- 配置条目按普通日志复制，**提交立即生效**：增/删后多数派按新集合计算；
- 被移除节点的迟到响应被忽略，且它不再能竞选；移除/降级任何节点都
  不会删除已提交数据——日志是集群复制状态，不随成员离开而丢失。

## 容错边界

| 故障 | 保证 |
|---|---|
| 少数派网络分区 | 少数派不能提交；多数派可继续选主与提交；恢复后冲突尾部被显式回滚并收敛 |
| 领导者被隔离 | 多数派选出更高任期领导者；旧领导者复联后降级，未提交提案不残留 |
| 节点宕机/重启 | 磁盘（任期、投票、日志、快照）保留，内存态重建，已提交日志重放不丢不重 |
| 消息重复 | 投票幂等、追加幂等、快照幂等；重复不改变最终状态 |
| 消息乱序 | 以逻辑时刻排序投递；一致性检查与任期归位保证乱序不破坏安全属性 |
| 长期落后 | 通过快照 + 增量日志恢复，不需要永久保留全量历史 |
| 增删节点 | 单成员串行变更，多数派按生效配置计算；已提交数据不随成员移除而丢失 |

边界与限制（本地教学型实现）：

- 需要**多数派存活且互通**才能推进提交；多数派同时永久宕机时不可用（CP 取舍）。
- 消息模型为请求-响应，模拟器在节点宕机期间直接丢弃到达消息（模拟不可达内存态）。
- 算法本身是单线程状态机，由模拟器串行驱动；不包含真实网络 IO、WAL 文件
  与真实时钟，生产使用需替换 `Storage`、增加持久化 WAL 与并发控制。
- 分区恢复后若多个节点超时持续撞在一起，可能经历若干轮**分票**（活性延迟，
  随机退避保证最终收敛；测试中以足够长的确定性窗口断言最终一致）。

## 失败原因如何区分

- 提案 API 返回哨兵错误：`ErrNotLeader`、`ErrChangePending`、
  `ErrNoChange`、`ErrCompacted`、`ErrClusterUnavailable` 等（见 `raft/errors.go`）。
- RPC 拒绝携带结构化 `RejectReason`：`stale-term`、`voted-another`、
  `log-behind`、`log-gap`、`snapshot-stale`、`unknown-node`……
  日志中会打印任期、双方日志位置与计票结果。
- 网络层单独统计 `partitioned / dropped / duplicated` 次数
  （`Network.Stats()`），可区分"消息根本没过网"与"对端拒绝"。

## 本地验证

要求 Go 1.25+（仅用标准库）。

```bash
# 全部确定性场景测试（重复运行结果一致）
go test ./... -count=10 -v

# 竞态检测
go test -race ./...

# 端到端演示（六阶段：复制→分区→重启→成员变更→快照追赶）
go run ./cmd/demo

# 打印每次计票、多数派判定、提交位置推进、冲突回退
go run ./cmd/demo -debug

# 更换随机种子，验证结论与种子无关
go run ./cmd/demo -seed 42
```
